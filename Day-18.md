
# Walkthrough: **[TShark](https://tryhackme.com/room/tshark)**


**TShark** is the command-line version of Wireshark used to capture, filter, and analyze network packets directly from the terminal. It is widely used by SOC analysts, incident responders, and threat hunters to investigate PCAP files, detect suspicious traffic, analyze protocols, and identify Indicators of Compromise (IOCs). Unlike Wireshark's graphical interface, TShark is lightweight, scriptable, and ideal for remote Linux servers and automation.

---

## Who is this for?

This room is designed for SOC Analysts, Incident Responders, DFIR investigators, Network Security Engineers, Threat Hunters, and cybersecurity students who want to analyze packet captures efficiently from the command line. Learning TShark helps analysts investigate network incidents without relying on graphical tools.

---

## What is it?

TShark is a command-line packet analyzer that reads live network traffic or existing PCAP files. It supports filtering, protocol analysis, packet statistics, field extraction, and scripting, making it a powerful tool for network forensics and automation.

---

## Where does this apply?

TShark is commonly used in enterprise SOCs, Security Monitoring Centers, Incident Response teams, Digital Forensics investigations, malware analysis, and cloud environments where GUI access is unavailable.

---

## When should you learn it?

After understanding networking basics and Wireshark fundamentals. TShark is especially valuable once you begin working with Linux servers, SIEM integrations, or automated security workflows.

---

## Why is it important?

Modern SOC analysts often investigate hundreds of PCAP files. TShark enables quick filtering, searching, and extraction of relevant evidence directly from the terminal, saving time during incident investigations.

---

## How does it work?

TShark reads packets from a network interface or PCAP file, decodes protocols, applies filters, extracts selected fields, and displays results in text format. Analysts can search for DNS queries, HTTP requests, suspicious IP addresses, unusual ports, and protocol anomalies using simple commands.

# **Task 2 – Reading PCAP Files**

## Question

**How many packets are in the [dns.cap](https://wiki.wireshark.org/SampleCaptures?action=AttachFile&do=get&target=dns.cap) file?**

### Answer

**38**


A **packet** is the smallest unit of network communication. Finding **38 packets** tells us the size of the capture and helps estimate how much traffic needs to be analyzed. Packet count is usually the first statistic analysts check.

## Question

**How many A Records are in the capture?**

### Answer

**6**


An **A Record** maps a domain name to an IPv4 address. Counting A records helps analysts understand how many DNS hostname-to-IP resolutions occurred. This is useful when investigating malware communication or DNS activity.

---

## Question

**Which A Record appeared most?**

### Answer

**GRIMM.utelsystems.local**


The most frequently requested hostname may represent a commonly accessed internal server or a system repeatedly communicating across the network. SOC analysts investigate repeated DNS requests to determine whether the behavior is normal or suspicious.

# **Task 3 – DNS Exfiltration**

## Question

**How many packets are in the capture?**

### Answer

**125**


This PCAP contains **125 packets**, giving analysts enough network evidence to investigate suspicious DNS activity and identify potential data exfiltration attempts.

---

## Question

**How many DNS Queries?**

### Answer

**56**


Only **DNS Requests** are counted—not the responses. Attackers often generate many DNS queries when using DNS tunneling or data exfiltration techniques.

---

## Question

**What is the suspicious DNS Transaction ID?**

### Answer

**0xbeef**


A **Transaction ID** uniquely identifies a DNS request and its corresponding response. A repeated or recognizable value like **0xbeef** can indicate custom scripts, malware testing, or intentionally crafted traffic.

---

## Question

**What string was extracted?**

### Answer

```text
MZWGCZ33ORUDC427NFZV65BQOVTWQX3XNF2GQMDVG5PXI43IGRZGWIL5
```


This encoded string is hidden inside DNS queries. Attackers commonly encode sensitive information using **Base32** or **Base64** before sending it through DNS to bypass traditional security controls.

---

## Question

**What is the flag?**

### Answer

```text
flag{th1s_is_t0ugh_with0u7_tsh4rk!}
```

The flag confirms that the hidden information was successfully extracted from DNS traffic. In real-world SOC investigations, analysts extract credentials, malware configurations, or stolen data instead of challenge flags.

#  Interview Scenario

**Scenario:** Your SIEM reports an unusually high number of DNS queries from a single workstation, with long encoded subdomains sent to an unknown external domain.

**Sample Answer:** I would verify whether the domain is legitimate, inspect the DNS queries for encoded or high-entropy strings, correlate with endpoint and firewall logs, determine if sensitive data may be leaving the network via DNS tunneling, and escalate the incident if malicious activity is confirmed.
